# 停车场管理系统项目深度分析

更新日期：2026-04-18  
分析对象：当前工作区 `D:\code\parking-management-system`  
分析结论基于当前仓库文件、配置、SQL 与测试结果，不假设工作区已经稳定收口。

## 1. 项目定位

这个项目本质上不是从零设计的一套独立平台，而是基于 RuoYi-Vue 做的业务化改造版本。底层仍然保留了若依的系统管理、权限、字典、参数、代码生成、定时任务等公共能力，停车业务作为一个独立模块接入。

从当前代码状态看，它已经超过“课程作业式 CRUD 拼装”的阶段，具备明确的业务模型、菜单体系、角色体系、全局配置、支付记录和统计概览。但它还没有完全进入稳定交付状态，仍处于一次较大的结构调整之后的整合期。

一句话概括：

- 基础平台：RuoYi 3.9.2 改造版
- 业务中心：`ruoyi-parking`
- 当前阶段：业务闭环基本成型，工程基线尚未完全收口

## 3. 模块结构与职责

### 3.1 停车业务模块规模

当前 `ruoyi-parking` 大致规模如下：

- 12 个 Controller
- 12 个 Service 接口
- 12 个 ServiceImpl
- 11 个 Mapper
- 12 个 Domain
- 2 个 DTO

对应前端 `ruoyi-ui/src/views/parking` 里有：

- 19 个 Vue 页面
- 12 个 parking API 文件
- 5 个共享页面组件

这说明停车模块已经具备完整前后端对应关系，不是单侧堆代码。

### 3.2 后端职责拆分

后端职责分层延续若依风格：

- Controller：权限、请求参数接入、分页、基础角色范围控制
- Service：业务编排、状态流转、计费、支付联动
- Mapper / XML：数据库访问
- Domain / DTO：业务对象与配置对象

停车模块中较核心的控制器包括：

- `ParkingOverviewController`
- `ParkingLotController`
- `ParkingSpaceController`
- `ParkingCustomerController`
- `ParkingUserVehicleController`
- `ParkingTempOrderController`
- `ParkingMonthlyOrderController`
- `ParkingMembershipOrderController`
- `ParkingPaymentRecordController`
- `ParkingSettingsController`
- `ParkingUserConfigController`
- `ParkingLotAdminController`

### 3.3 前端职责拆分

前端结构也比较清楚：

- `src/views/parking/index.vue`：工作台/概览页
- 各业务页面：车场、车位、客户、车辆、临停、月卡、会员、支付、设置
- `src/views/parking/components/`：表格、搜索、表单壳子
- `src/api/parking/*.js`：与后端 API 一一对应

前端菜单不是写死在本地路由里，而是走若依的动态菜单机制：

1. 登录后前端请求 `/getRouters`
2. 后端根据用户角色返回菜单树
3. 前端在 Vuex `permission` 模块中转换为路由
4. 再将动态菜单渲染到侧边栏

因此，停车系统能否正常展示菜单，核心取决于 `sys_menu` 初始化是否正确，而不是单纯有没有页面文件。

## 4. 数据库设计

### 4.1 当前数据库基线

停车模块当前已经把 SQL 合并成一个总初始化脚本 `sql/parking/parking_init.sql`。从脚本头注释看，它意图一次性完成：

1. 10 张业务表 DDL
2. 最小演示数据
3. 菜单初始化
4. 全局配置种子
5. 字典种子
6. 角色与测试用户

### 4.2 业务表划分

当前 10 张停车表可以分成 4 类：

基础档案：

- `parking_lot`
- `parking_space`
- `parking_customer`
- `parking_user_vehicle`
- `parking_lot_admin`

订单类：

- `parking_temp_order`
- `parking_monthly_order`
- `parking_membership_order`

支付类：

- `parking_payment_record`

个性化配置类：

- `parking_user_config`

### 4.3 设计特点

几个设计点是值得肯定的：

- `parking_customer` 通过 `user_id` 关联 `sys_user`，但大多数业务对象使用 `customer_id` 作为业务身份主键
- `parking_lot_admin` 继续保留 `user_id` 绑定内部账号，边界相对清晰
- 支付记录和业务订单分离，方便级联生成支付流水
- `parking_user_config` 将“快捷入口”等用户偏好独立存储，没有污染全局配置

### 4.4 历史包袱

`parking_lot` 表里仍然保留了 `monthly_price`、`temp_hour_price` 两个字段，但从代码趋势看，新的计费规则已经开始往全局配置迁移，说明项目正处于“从按车场局部价格转向全局规则”的过渡阶段。

## 5. 业务能力拆解

### 5.1 工作台与概览

工作台不是静态首页，而是具备实际业务统计能力：

- 停车场总数
- 总车位/空闲车位/占用车位
- 今日入场/出场/营收
- 活跃临停订单
- 最近订单
- 快捷入口配置

概览服务会根据当前用户身份决定是否做车场范围过滤。管理员看全局，停车场管理员看绑定车场范围。

### 5.2 临停订单

临停订单已经具备一条完整的状态流：

- 新建
- 入场
- 出场
- 计费
- 结算
- 生成支付流水
- 释放车位

同时，临停费用已经接入全局规则：

- 小时单价
- 免费分钟数
- 计费步长
- 是否向上取整
- 每日封顶金额
- 会员折扣

这是当前业务实现里最完整的一条链路之一。

### 5.3 月卡与会员订单

月卡和会员订单也都具备：

- 创建
- 修改
- 支付
- 取消
- 折扣重算
- 生成支付流水

其中月卡订单已经支持通过 `vehicleId` 回填车牌，不再强依赖人工输入车牌号，说明产品交互层面已经做过一轮优化。

### 5.4 支付流水

支付记录既支持手工新增/修改/退款，也支持由订单成功结算时级联生成。当前默认支付渠道、现金开关等规则已经向配置化靠拢，但支付本身仍是“内部模拟流水模型”，并没有接真实三方支付。

### 5.5 全局停车设置

这是当前仓库里最明显的新能力之一。

停车设置已经覆盖：

- 月卡全局价格
- 临停小时单价
- 免费分钟数
- 计费步长
- 向上取整
- 封顶金额
- 会员折扣开关
- 银卡/金卡/铂金折扣率
- 默认支付渠道
- 现金支付开关
- 取消自动退款开关

这些规则统一落在 `sys_config`，支付渠道等枚举落在 `sys_dict`，方向是对的，也更符合若依本身的系统能力设计。

## 6. 权限与角色模型

### 6.1 角色划分

当前业务角色至少包括：

- `admin`
- `lot_admin`
- `customer`

角色、菜单和测试用户已经在 `parking_init.sql` 里初始化。

### 6.2 菜单组织

停车菜单不是平铺，而是被组织为三个业务导航根：

- `archives`：基础档案
- `operations`：运营中心
- `customers`：客户中心

此外还有一个单独的工作台 `parking` 入口。

这说明菜单设计不是单纯“把页面挂上去”，而是已经做过一轮信息架构整理。

### 6.3 当前权限实现水平

当前权限实现已经做到了：

- 页面按钮级权限控制
- 后端接口 `@PreAuthorize`
- 菜单级动态路由
- 列表接口的角色范围限制

但它还没有彻底做到对象级权限闭环。

## 8. 主要风险与问题

### 8.1 SQL 基线漂移

这是当前最直观的问题。

仓库已经把多个 SQL 脚本合并进 `parking_init.sql`，但以下内容仍然保留旧引用：

- `docker-compose.local.yml`
- `LOCAL-SETUP.md`
- `ParkingSchemaScriptTest`
- `ParkingMenuScriptTest`
- `ParkingUpgradeScriptTest`

这会直接导致：

- 本地初始化脚本路径失效
- 测试持续失败
- 新人接手时按文档无法直接起库

### 8.2 工作区处于脏状态

当前 `git status` 显示 parking 后端、前端、SQL、测试和文档均有大量未提交改动。说明当前仓库更接近“开发中的整合分支”，而不是稳定主干。

这意味着现在看到的状态，未必是一次完整、已验证的提交面。

### 8.3 对象级权限控制不足

这是最需要重视的业务风险。

当前很多控制器只在 `list` 接口上根据角色注入 `lotId` 或 `customerId` 过滤，但对以下接口没有看到同级别的对象归属校验：

- 详情查询
- 修改
- 支付
- 取消
- 入场
- 出场
- 结算
- 删除

典型表现：

- 停车场管理员和普通客户的列表被限制了
- 但只要拿到别人的订单 ID，部分接口理论上仍可能越权操作

这是一个真实的安全与业务边界问题，比文档不一致更优先。

### 8.4 前端文案与编码一致性问题

仓库里一部分页面和测试文件明显出现过编码问题。当前并不是所有中文都正常，有些文件能读到正常中文，有些文件则出现乱码式字符串。

这会影响：

- smoke test 稳定性
- 页面一致性
- 后续维护人员的修改效率

### 8.5 支付仍是内部模拟模型

当前支付模块更像“停车业务记账模型”，而不是第三方支付接入。它适合内部演示、业务流验证和后台管理，但如果后续目标是真实商用，还缺：

- 对账
- 回调
- 幂等
- 外部单号状态同步
- 渠道失败补偿

## 9. 项目成熟度判断

如果按阶段评估，我会这样判断：

- 业务原型：已经完成
- 管理后台 MVP：基本完成
- 团队内演示版：可以支撑
- 对外稳定交付版：还不够

原因不是它功能少，而是它仍缺少以下收口动作：

- SQL 与文档统一
- 测试基线统一
- 权限边界补全
- 编码/文案一致性清理
- 脏工作区整理成可追踪提交

## 10. 建议的后续治理顺序

建议不要继续先堆新功能，优先按下面顺序治理。

### 第一阶段：基线收口

目标：让“起库、跑测、看菜单、看页面”重新一致。

建议动作：

1. 统一 SQL 方案，只保留一种正式入口
2. 修正 `docker-compose.local.yml` 与 `LOCAL-SETUP.md`
3. 更新脚本相关测试，让它们对准 `parking_init.sql`
4. 确认菜单初始化方案是否彻底从 `parking_menu.sql` 合并到总脚本

### 第二阶段：权限补洞

目标：让角色范围不仅体现在列表，也体现在对象操作。

建议动作：

1. 为订单、支付、车辆、客户等对象增加“当前用户是否可操作该记录”的统一校验
2. 把 `lot_admin` 和 `customer` 的对象归属校验下沉到 service 层
3. 为这些权限边界补专门测试

### 第三阶段：前端和文案一致性整理

目标：让界面、测试和源码编码重新统一。

建议动作：

1. 逐步修复乱码文件
2. 统一菜单标题、页面标题、按钮文案
3. 修正 smoke test 里的旧预期和编码异常

### 第四阶段：再考虑扩展功能

如果前 3 个阶段做完，再继续考虑：

- 到期自动失效
- 统计报表
- 真实支付接入
- 多车场更强的数据隔离
- 操作审计增强

## 11. 最终结论

这个仓库最大的价值不在于“若依 + 一些停车表”，而在于它已经形成了一套相对完整的停车场后台业务模型：档案、订单、支付、角色、菜单、规则、概览都已经接上了。

当前最核心的判断不是“能不能继续做功能”，而是“是否应该先把工程基线拉回一致”。我的结论是：应该先收口，再扩展。

如果当前目标是继续接手开发，这个项目最合理的切入点不是新增页面，而是：

1. 先修 SQL/文档/测试基线
2. 再补对象级权限
3. 最后再谈新功能

这样做的收益最大，也最能降低后续返工。
